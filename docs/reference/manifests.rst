Manifests and configuration
===========================

.. include:: ../_includes/paid-cloud.txt

Three files describe different kinds of intent: a repository's BACON manifest,
its generated lock, and a local environment manifest. The repository files are
portable. The environment manifest supplies machine-specific names and paths.

File locations
--------------

Paths below are relative to ``HMD_HOME`` unless marked repository-relative.

.. list-table::
   :header-rows: 1

   * - Location
     - Purpose
   * - ``environments/<slug>.yaml``
     - Desired instances, substrate, and adoption bindings for an environment
   * - ``.config/control-plane.yaml``
     - Shared control-plane extensions
   * - ``.config/hmd.env``
     - HMD environment-variable configuration
   * - ``.config/nsctl.toml``
     - Tenant authentication and service profiles
   * - ``.cache/neuronsphere/environments.json``
     - Registry: accounts, names, port slots, state directories, default environment
   * - ``.cache/tokens.yaml``
     - Shared login credential cache; not source-controlled configuration
   * - ``.cache/neuronsphere/artifacts/``
     - Unpacked artifact repository trees
   * - ``.cache/neuronsphere/versions/``
     - Cached answers to published-version queries
   * - ``meta-data/manifest.json`` (repository-relative)
     - BACON class metadata and local requirements for adoption
   * - ``neuronsphere.lock`` (repository-relative)
     - Concrete dependency versions generated by ``nsctl lock``

Do not reconstruct resource names from a slug or edit the registry to move an
environment. Names and paths are persisted at registration, including legacy
layouts. Use registry commands to select and manage entries.

Environment manifest discovery
------------------------------

``HMD_LOCAL_ENV_MANIFEST`` overrides discovery. Otherwise, the loader searches
``environments/<slug>.yaml``, then ``.yml``, then ``.json``. With no manifest,
the environment has only its substrate. A missing substrate value means
``full``.

Example declaration
-------------------

This example describes a local checkout with two dependency roles. Replace the
class and absolute path with a repository you have, and use the role names its
manifest declares::

   version: 1
   name: dev
   substrate: full
   repos:
     - instance_name: my-api
       repo_class_name: hmd-ms-myapi
       version: "0.3"
       source:
         type: local
         path: /work/hmd-ms-myapi
       instance_configuration:
         replicas: 2
       dependencies:
         eks-cluster: eks-cluster
         database-instance: environment-db

Top-level fields
----------------

.. list-table::
   :header-rows: 1

   * - Field
     - Meaning
   * - ``version``
     - Manifest schema version, currently ``1``
   * - ``name``
     - Name recorded in the declaration
   * - ``substrate``
     - ``full``, ``core``, or ``none``; default ``full``
   * - ``repos``
     - List of desired workload instances
   * - ``profiles``
     - Active local profile names recorded by repository adoption
   * - ``bindings``
     - Maps dependency roles, companion names, and the subject class to local instances
   * - ``plugins``, ``plugin_config``
     - Python CLI settings, preserved but not acted on by nsctl

The environment manifest is stored under ``HMD_HOME``, not automatically
inside an adopted checkout. Its ``bindings`` and absolute paths can differ
between developers sharing one repository lock.

Instance fields
---------------

Every entry names ``instance_name`` and ``repo_class_name``. The instance is
the local deployment identity; the class identifies its implementation.
Do not declare substrate-owned instance names as application workloads.

``dependencies`` maps a dependency role to the instance supplying it.
``instance_configuration`` carries per-instance values layered with the
class configuration during deployment.

A missing ``source`` or source type means ``local``. For a local source,
``source.path`` wins over ``$HMD_REPO_HOME/<repo-class>`` and environment
variables in the path are expanded. Tilde expansion is a shell feature; use
an absolute path or an environment variable in a manifest.

For a published source, use a concrete version::

   instance_name: my-api
   repo_class_name: hmd-ms-myapi
   version: "0.3.12"
   source:
     type: artifact
     artifact_type: build

``artifact_type`` defaults to ``build``. Fetch the artifact before applying.
See :doc:`../how-to/artifacts-and-locks`.

Control-plane extensions
------------------------

The shared manifest uses the same repository-list shape::

   version: 1
   name: control-plane
   repos:
     - instance_name: package-registry
       repo_class_name: hmd-inf-local-registry
       version: "0.1.4"
       source:
         type: artifact
       instance_configuration:
         pypi:
           enabled: true

Use a version available in your librarian. The extension's
``src/local/docker-compose.extension.yml`` joins the control-plane Compose
project; it does not deploy into an environment cluster. Extensions cannot pin
container names, publish host ports, or use named volumes. The proxy handles
external routing.

``control-plane repo add|remove|list`` manages declarations, and
``control-plane apply`` converges them. Startup applies them too. An extension
failure is reported separately and does not prevent the base control plane
from starting.

An extension can contribute configuration back through a managed block in
``.config/hmd.env``. User values take precedence; map and list values merge
according to the declared handback strategy. See
:doc:`../plugins/development` for the complete extension contract.

Configuration precedence
------------------------

``--home`` overrides the process's ``HMD_HOME``. Once the home is selected,
process environment variables override values loaded from
``$HMD_HOME/.config/hmd.env``.

Tenant profiles are separate from local workload profiles. A
``[profile.acme]`` table in ``nsctl.toml`` selects cloud authentication and
services. A ``local.default_profiles`` list in a repository manifest selects
optional local workloads. The command determines which meaning its
``--profile`` flag has; the two are not interchangeable.

Apply after editing
-------------------

For an environment, inspect with ``nsctl env plan dev`` and deploy with
``nsctl env apply dev``. For the shared control plane, use
``nsctl control-plane apply``. Editing a file alone does not reconcile running
resources, and removing an environment instance declaration does not destroy
its deployed resources.
