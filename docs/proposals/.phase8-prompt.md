## 1. The verification, in dependency order

Each of these has a written expected outcome. Where the outcome differs, the
NERD is what gets corrected -- not the expectation quietly.

**a. Item 4 first, because it is the one the requirement rests on.** The top of
the NERD says "a single binary whose only prerequisite is Docker". Until
2026-09-07 that was false of everything past `control-plane start`. The test is
a machine with no `HMD_REPO_HOME`: point it at an empty directory, purge,
`nsctl env add` a **new** environment with no manifest, and cold `env start`.
The substrate must deploy from bundled trees alone and the cluster must come up
with External Secrets on it.

It must be a new environment. `local`'s manifest was written by the Python CLI
and carries the ext-secrets entries already, so it would hide exactly the
missing declaration this item added.

Expect the bundled trees to be *nearly* right rather than right. They are copies
of ten repos taken with rsync and packed by `tools/repopack`, excluding build
outputs and `meta-data/resources_output`. A deploy that reads something the
exclusion list dropped will fail in that repo's own deploy script, several
layers from the cause. Widen the list, do not special-case a repo.

**b. Item 4's second half, separately, because nothing fails when it is wrong.**
Bring up a second environment and confirm the two ext-secrets operators
authenticate as *different* accounts -- compare the rendered `localAccessKeyId`,
or `AWS_ACCESS_KEY_ID` in each operator pod. One Floci serves every account and
reads the account off the 12-digit key, and the secret names are identical
across environments, so a shared key means one environment silently reads the
other's secrets and everything looks fine.

**c. Item 2.** Purge an environment; `docker ps -a`, `docker volume ls` and
`docker network ls` must show nothing belonging to it and `nsctl env list` must
not list it. Then `env add` and `env start` the same name and confirm a clean
cold start -- a path that works now, so a purge that left something behind
surfaces as a bootstrap failure rather than silently.

The ordering claim is what the unit tests assert and what a real run can
disprove: Floci-hosted resources are deleted through Floci *before* the control
plane stops. Watch for the Python's symptom in nsctl's output --
`Could not connect to the endpoint URL "http://localhost:4566/"` -- which would
mean the ordering is right in the test and wrong in the wiring.

**d. Item 1.** With the runner enabled,
`HMD_LOCAL_SERVICE_SUBMIT=1 nsctl env start <env>` must reach "waiting for the
control plane to submit the workflow..." and then actually get one.

**This path has still never run.** Phase 4's *Not done* names the expected next
obstacle: `call_deploy_change_set_deployment`, an async self-invoking Lambda
whose behaviour under Floci is unverified. It is reachable now and that is all
that changed. If it does not work, say so and amend the SPEC -- do not leave the
flag half-wired a second time.

Note the warm-start path specifically: `syncRunnerSelection` reconciles
`HMD_WORKFLOW_RUNNER_URL` onto an already-deployed ms-deployment Lambda, and a
machine whose control plane predates this commit is the only place that code
runs. Toggle `HMD_LOCAL_NEURONSPHERE_ENABLE_RUNNER` off and on across two starts
and confirm the variable follows in both directions.

**e. Item 6.** Run the parity suite to completion --
`make test-parity NSCTL_PARITY_ENV=<slug>`. It has never finished a run. It
starts and stops a real environment, which is why it demands the environment be
named; do not remove that guard.

**f. Item 5.** The Traefik warning only fires on a cluster predating the
baked-in ingress. If you have no such cluster, say so rather than manufacturing
one -- a synthetic reproduction of a migration would prove the grep works and
nothing else.

## 2. What is open independently of that

- **SPEC012 stays `partly implemented`.** The harness covers `env start`,
  `env stop`, `status` and the registry. Extending it is real work with a real
  payoff, but scope it deliberately: the suite needs a platform per run, so
  every verb added costs wall-clock on every run.
- **Phase 5's *Not done*: nothing measures a real cold bootstrap's speedup**,
  only a synthetic DAG of the same shape. Now that a cold start works from
  nothing, this is finally measurable. Expect a smaller gain than the synthetic
  8s-against-21s -- the real one is dominated by container pulls and Terraform
  -- and record the real number even if it is unflattering.
- **The eight unfetched bundled classes.** Only `hmd-inf-ext-secrets` and its
  CRDs are declared as `pre_build_artifacts`; no repo in the monorepo pins the
  other eight, so whether they publish a consumable `build` artifact is
  unverified and they travel as committed trees. If they do publish one, move
  them to the fetch path and shrink `bundled-repos/`. **Verify each artifact
  resolves before pinning it** -- an entry that does not exist breaks
  `hmd build` for everyone, which is why it was not done blind.
- **SPEC014: `hmd-ms-artifact-lib`'s `BUCKET_NAME`.** The SPEC names the exact
  edit (`deploy.default_configuration`, where `floci.ServiceParameters` already
  reads). It is a change in that repo and nothing here can close it. Either make
  it there or accept it in writing; it has been "reported rather than closed"
  for long enough that the distinction is wearing thin.
- **SPEC014: the container-name collision is detected, not fixed.** Two
  `HMD_HOME`s still cannot run control planes concurrently. The SPEC says why
  the rename is a breaking change and what Floci's `neuronsphere` alias
  prevents. Leave it unless you intend the whole rename.

## 3. Flipping the requirement

`.. req::` at the top of the NERD is still `:status: in progress`. The honest
gate is 1a: a machine with no `HMD_REPO_HOME` deploying an environment. That is
the requirement's own sentence. If 1a passes and 1d does not, the requirement
can still flip -- the inverted submit path is opt-in and always was -- but say
so explicitly in the Implementation Status table rather than letting a green
table imply it.

## Traps

- **A guarded find-first step is invisible on a warm graph.** Five bootstrap
  defects hid behind guards that returned early because the Python CLI had
  seeded the graph. Anything you touch in the seeding path must be exercised
  against an empty graph, which means a genuine purge and cold start, not a
  restart.
- **`HMD_HOME` is not consent.** `make test-parity` starts and stops a real
  environment and now refuses without `NSCTL_PARITY_ENV`. That guard exists
  because the suite was run at a live platform by reflex during its own
  development. The same reflex applies to every command in section 1.
- **Do not start a control plane against a throwaway `HMD_HOME`.** The container
  names are global; `nsctl` now refuses rather than recreating another home's
  containers, but the refusal is the *only* protection and it is one commit old.
- **`make check`, `make test-race` and `make test-cli` must all stay clean.**
  CI runs all three. `make test-parity` is deliberately not among them.
- **The bundled trees are verbatim copies.** They are excluded from black for
  that reason. If a formatter or an editor reformats one, `make
  refresh-bundled-repos` will show it as a diff forever.

## Conventions

Conventional commits, reasoning in the body rather than the diff. Update
CHANGELOG.md (feat/fix/refactor/test only). Update the NERD as you go: the
SPEC's status, its table row, and the phase entry. When verification shows the
document asserted something untrue, that belongs in "What implementation changed
about the design" -- fifteen items now, each a bold claim, the SPEC, and the
correction. A verification that passes is worth recording too: the table's notes
currently describe what was built, and "and it has been run from nothing" is a
different and stronger sentence.
