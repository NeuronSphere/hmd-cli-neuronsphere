Close out NERD0002: the work left after Phase 6 and the cold-start fixes.

Repo: hmd-cli-neuronsphere, branch feat/nsctl-go-cli. Phases 0-6 have landed,
plus an unplanned seventh pass that made the cold start work.
Read docs/proposals/NERD002_Go_CLI_Port.rst first -- the Implementation Status
table, the "What implementation changed about the design" list (twelve items),
and "The cold start had never run". Between them they are the spec for this.

This is not one feature. It is six independent items with one thing in common:
each is a claim the document makes that the code does not keep. Commit each
separately.

**Item 4 is the one that matters.** A `brew install`ed nsctl cannot deploy an
environment today -- the substrate's first node fails looking for a working
tree that a distributed binary has no reason to have -- so the whole of Phase
6's distribution work currently ships something that stops after
`control-plane start`. Items 1-3 are ordered cheapest-first ahead of it because
they are quick and 1 has a written answer already, but if time is short, do 4.

## 1. `HMD_WORKFLOW_RUNNER_URL` is never set

The smallest item and the one with a written answer. Phase 4's *Corrected*
note says where it goes; follow it.

`hmd-ms-deployment` reads the variable (`deployment_manager.py:86`, with
`test_runner_selection.py` covering both branches). Nothing sets it, so
`HMD_LOCAL_SERVICE_SUBMIT=1` seeds a changeset, waits two minutes for a
workflow nobody submitted, and fails "no workflow appeared".

It belongs in `floci.ServiceEnv`'s map, for `hmd-ms-deployment` only.

- **The address is in-network, not the host route.** The Lambda runs inside
  Floci on the neuronsphere network: `http://hmd_nsrunner:8080`.
  `http://localhost/nsrunner` is the host route and resolves to the wrong
  thing (or nothing) from inside a container.
- **Gate it on the runner being enabled** (`controlplane.RunnerEnabled`). A
  control plane told to submit to a runner that is not running fails *every*
  deploy, where today it falls back to in-process execution. That fallback is
  the thing you would be destroying.
- `ServiceEnv` is shared by all four foundation services and takes no options
  today. Adding a per-service value there needs a little care; do not give
  ms-naming a runner URL.

*Verify:* with the runner enabled, `HMD_LOCAL_SERVICE_SUBMIT=1 nsctl env start
local` must reach "waiting for the control plane to submit the workflow..." and
then actually get one. That path has never run, so expect the async
self-invoking Lambda (`call_deploy_change_set_deployment`) to be the next
obstacle -- Phase 4 flagged its behaviour under Floci as unverified and it has
still never been reached. If it does not work, say so and amend the SPEC
rather than leaving the flag half-wired again.

## 2. `nsctl env purge`

The last missing verb (SPEC001, SPEC002, named as outstanding in four places).
`nsctl env delete` is a registry edit only -- read its Long text, which is
explicit that it is not a teardown.

The Python equivalent is `stop_environment(env, purge=True)` in
environments.py around line 1770. Port what it does, and **do not port what it
gets wrong**, because a purge is the one operation where leftovers are the
whole failure mode. Observed on 2026-09-07, purging by hand afterwards:

- It stops Floci *before* asking Floci to delete the resources Floci spawned,
  so every purge warns `Could not delete the control-plane RDS instance: Could
  not connect to the endpoint URL "http://localhost:4566/"` and leaves the RDS
  and Neptune containers and **every one of their volumes** behind. 49 stale
  `floci-*` volumes had accumulated. Delete the Floci resources first, then
  stop Floci.
- A `hmd-img-projectbuilder` container from an interrupted deploy survives,
  holds the network open, and cannot be swept: it has a Docker-generated name
  (`quirky_bassi`) and no label tying it to the environment. Consider labelling
  projectbuilder containers at launch (`internal/runner`) so a purge can find
  them; that is a small change with no other consumer.
- The environment's nginx fragments, state dir, kubeconfig and registry entry
  all have to go, and the registry entry must go *last* -- an unregistered
  environment whose containers still run is the state `env delete` warns about.

*Verify:* purge an environment, then `docker ps -a`, `docker volume ls` and
`docker network ls` must show nothing belonging to it, and `nsctl env list`
must not list it. Then `env add` + `env start` the same name and confirm a
clean cold start -- which is now a path that works, so a purge that leaves
something behind will show up as a bootstrap failure rather than silently.

## 3. Control-plane containers are not namespaced by `HMD_HOME`

SPEC014 records this gap and says "nothing currently detects it". It is not
theoretical: it destroyed a running platform during this session's work.

`hmd_proxy`, `floci`, `hmd_deployment_gui` and `hmd_nsrunner` are fixed
`container_name:` values in docker-compose.control-plane.yml (lines 10, 42,
142, 230), while networks, compose projects and Floci data directories are all
already namespaced by an `HMD_HOME` hash. So starting a control plane in a
second `HMD_HOME` silently recreates the first one's containers pointed at the
new home, and killing that start leaves the first with no proxy at all.

Two options, and the SPEC does not choose:

- **Detect and refuse.** Cheap and safe: on start, if a container exists whose
  `com.docker.compose.project` label names a different project than this
  `HMD_HOME`'s, refuse with both paths named. This is the minimum, and it is
  what "detected and named, not silently mishandled" asks for.
- **Namespace the names.** Correct, and a breaking change: every consumer that
  addresses `hmd_proxy` or `floci` by name -- the compose file's own aliases,
  nginx fragments, the Robot suites, `/etc/hosts` guidance -- would have to
  follow. Note that Floci's network *alias* (`neuronsphere`) is baked into
  presigned URLs and cannot simply move.

Recommend one in the SPEC before building it. If you detect-and-refuse, say
plainly in the SPEC that the underlying collision remains.

## 4. Bundle the core repo trees (SPEC006) -- required, not optional

**This is the item that decides whether Phase 6 meant anything.** Today a
Homebrew-installed `nsctl` cannot deploy an environment at all. The first
substrate node fails at runner.go:177 with

    no working tree for hmd-vpc under <HMD_REPO_HOME>; clone it there, or
    declare an explicit source path in the environment manifest

so "a single binary whose only prerequisite is Docker" (the requirement at the
top of the NERD) is not true of anything past `control-plane start`. Bundle the
trees the base control plane and core environment need. Raising SPEC013's
50 MB budget was offered and is not necessary -- see the measurements below --
but the requirement stands regardless of what it costs.

**The six artifacts in meta-data/manifest.json are only partly the right
list.** Four of them -- superset, hyperdx, telemetry-debug, s3bucket -- are
workloads or plugin content and are not wanted. The other two,
`hmd-inf-ext-secrets` and `hmd-inf-ext-secrets-crds`, **are** wanted, but not
for the reason the manifest declares them: they were pre-build artifacts so
`k3s_operators.py` could `helm upgrade --install` them directly, and that path
is dead. They are now default BOM entries (`bom_seeder.py:368`, and its own
comment at line 303 -- "dead code once ext-secrets is part of the BOM"), so
they deploy as ordinary DAG nodes, which is exactly how nsctl ran them:
`ext-secrets-crds` and `ext-secrets` were nodes 2 and 7 of the last cold start.
That means they hit the same runner.go:177 failure as everything else, and need
bundling for the same reason.

So the set is the RepoClasses nsctl's bootstrap and substrate deploy, plus the
two operators every cloud chart's rendering depends on. None is bundled today:

| RepoClass | why | approx. gz |
|---|---|---|
| `hmd-vpc` | base-vpc, and the control plane's VPC | 10 KB |
| `hmd-postgres-rds` | environment-db, and control-plane-db | 20 KB |
| `hmd-inf-neptune` | control-plane-graph, global-graph | 10 KB |
| `hmd-inf-eks-cluster` | eks-cluster | 10 KB |
| `hmd-ms-naming` | foundation service | 10 KB |
| `hmd-ms-artifact-lib` | foundation service | 10 KB |
| `hmd-ms-deployment` | foundation service | 190 KB |
| `hmd-ms-dbaccount` | per-environment service | 10 KB |
| `hmd-inf-ext-secrets-crds` | the CRDs every `ExternalSecret` needs | 143 KB |
| `hmd-inf-ext-secrets` | the operator that reconciles them | 40 KB |

**~460 KB gzipped in total**, measured over `meta-data/` and `src/` with
build/target/.git excluded, and dominated by ms-deployment and the CRDs.
Against a 34.4 MB binary that is noise: the size question this item was
previously framed around does not exist. Re-measure rather than trusting the
table, but do not go looking for a trade-off.

**Declare them as well: they go in `bom.Substrate()`.** Today the two entries
reach nsctl only through the environment manifest, which on a developer machine
the Python CLI wrote -- so an environment created by `nsctl env add` alone gets
a cluster with no External Secrets, and the first cloud chart rendering an
`ExternalSecret` fails on it. Bundling the repo does not fix that; declaring
does.

This is a deliberate widening of what "substrate" means, and SPEC001, SPEC002
and docs/nsctl.rst all currently say an environment is "a cluster and a
database with nothing on them". Update that wording: it is now a cluster, a
database, and the operator that lets a cloud chart's secrets resolve.

Mirror `bom_seeder.EXT_SECRETS_BOM` rather than inventing the entries -- it is
about seventy lines of comment explaining values that are not guessable, and
all of them still apply:

- **CRDs first**, as a separate instance. `ext-secrets-crds` depends on
  `{eks-cluster, compute}`; `ext-secrets` on those plus `{crds: ext-secrets-crds}`.
  `installCRDs` is `False` in the chart values precisely because the prior
  entry owns them.
- **The chart's cloud defaults do not work locally.** They authenticate
  ClusterSecretStores via IRSA against `sts.<region>.amazonaws.com`, which
  resolves nowhere here, and the store sits at `InvalidProviderConfig` while
  every `ExternalSecret` silently never syncs. `_EXT_SECRETS_LOCAL_CONFIG`
  (bom_seeder.py:322) is the override; copy it.
- **`dockerRepoSecret` must target `aws-parameter-store`**, not the Secrets
  Manager store. The local CDKTF overlay writes the value with
  `hmd_lib_secrets_backend.create_secret()`, which always writes to SSM
  Parameter Store whatever its naming suggests. A Secrets Manager store would
  look in the wrong place and report "Secret does not exist".
- **Do not set `aws_region`.** hmd-cli-helm's `_set_local_standard_values`
  applies it with `--set`, which unconditionally beats a values file, so a key
  here is silently clobbered.
- **Opt-out is `HMD_LOCAL_NEURONSPHERE_ENABLE_EXT_SECRETS=false`**, matching
  the Python. Honour it, the way `k3sEnabled` already gates the cluster entry.

**The trap here is the account, and it has bitten before.** `localAccessKeyId`
selects which emulated AWS account the operator's lookups resolve in -- one
Floci serves every account and reads the account out of the 12-digit access
key. The Python rewrites it per environment in `_inject_floci_account()`, and
its comment records what happens otherwise: "an environment ended up silently
authenticating as the control plane". nsctl has no equivalent.
`bom.InjectEndpoints` is the right home -- it already rewrites
`environment-db` and `eks-cluster` per environment and runs inside `Seed`,
which is the one funnel every changeset passes through -- but it currently
handles exactly those two instances and nothing else. Extend it, and test that
two environments get different keys, because the failure is silent: the
operator works, reads the wrong account's secrets, and nothing errors.

There are two distinct consumers and they need different things:

- `repoclass` reads `meta-data/VERSION`, `manifest.json` and
  `config_local.json` -- that is what `ResolveVersion` and
  `floci.ServiceConfig` use, and a foundation service with no
  `service_config` starts and 500s on every request.
- `runner.repoPath` needs the **whole tree on a host path**, because
  projectbuilder is a sibling container and the daemon resolves its bind mounts
  on the host. A tree that exists only inside the binary is not mountable.

The second is the real design problem, and this codebase already solved its
twin: `EnsureRunnerImage` unpacks embedded sources to
`$HMD_HOME/.cache/neuronsphere/nsrunner-src` and builds from there. Do the same
-- materialise a bundled tree under `.cache` and point `repoPath` at it -- and
keep the precedence `ResolveVersion`'s comment already commits to: an artifact
beats a working tree, matching `bom_seeder.resolve_repo_version`, because a
published artifact is a reproducible version and a tree is a work in progress.
A working tree in `HMD_REPO_HOME` must still win when the user explicitly pins
or declares a source path, or local development of these repos becomes
impossible.

**The hard part is the build, not the embedding.** `pre_build_artifacts` are
fetched by `hmd build` from the artifact librarian. `make generate` is
self-contained today and runs with no network and no credentials -- which is
what lets GoReleaser call it from `before.hooks` on a clean CI checkout. If
embedding the trees makes `make build` depend on `hmd build` having run first,
every release breaks. Decide that deliberately: commit the trees, have
`make generate` fetch them with a documented fallback, or pack them from
`HMD_REPO_HOME` when present and fail the *release* build (not the dev build)
when absent. Whatever you choose, `goreleaser build --snapshot --clean` from a
fresh clone must still work, because that is the path that produces what users
install.

*Verify:* the honest test is a machine with no `HMD_REPO_HOME` at all. Set it
to an empty directory, purge, `nsctl env add` a *new* environment with no
manifest, and cold `env start`: the substrate must deploy from bundled trees
alone, and the cluster must come up with External Secrets on it. That is the
scenario Phase 6's distribution work was for and the one nothing has ever
exercised -- note it needs a new environment, not the existing `local`, whose
manifest the Python CLI wrote and which would hide a missing declaration.

Then, separately, bring up a second environment and confirm the two operators
authenticate as different accounts. Comparing the rendered
`localAccessKeyId` -- or the `AWS_ACCESS_KEY_ID` in each operator pod -- is
enough. Nothing fails if they match, which is why it needs asserting.

## 5. The two SPEC014 gaps with no code behind them

Both are recorded as gaps and neither has an implementation.

- **`hmd-ms-artifact-lib`'s bucket is declared only in
  `src/local/nsplugin.json`**, which nsctl deliberately does not read (SPEC005
  is withdrawn). nsctl bootstraps the service, says it will not serve until the
  bucket is in the manifest, and carries on. The fix is in *that* repo's
  manifest, not here -- but nothing tracks it, and the SPEC should either name
  the change needed or accept it permanently.
- **Two host-only helm paths were dropped**, and only one is still live.
  SPEC014 says both "must be detected and named, not silently mishandled", and
  grep confirms no such detection exists -- but the ext-secrets half is moot:
  the direct `helm upgrade --install` it names is dead in the Python too, since
  ext-secrets became a BOM entry, and item 4 bundles the repo so nsctl can
  deploy it as a node. Amend SPEC014 to say so rather than building detection
  for a path nothing takes. What remains live is the one-time `helm uninstall
  traefik` migration: a cluster predating it needs the Python CLI, and nothing
  tells its owner that. Detect it or accept it in writing.

## 6. The parity harness (SPEC012)

SPEC012 proposes "a parallel suite parameterised on the binary under test
(`hmd neuronsphere` vs `nsctl`)" and it was never built. Its absence is why
docs/nsctl.rst and the README carry a "What it does not do yet" section instead
of recommending nsctl outright, and why SPEC012 is `partly implemented`.

test/nsctl_cli.robot is the model for the mechanics -- it takes `${BINARY}`
from `make test-cli` and needs no Docker -- but the parity suite by definition
needs a platform, so it belongs with the existing Docker-dependent suites and
must not be wired into `make test-cli` or CI.

Scope it honestly. Full parity across every verb is a large suite; the useful
core is the acceptance test SPEC012 already states: "perform the operation with
one front end, verify with the other", for `env start`, `env stop`, `status`
and the registry. If you build only that, say so in the SPEC.

## Not in scope

- **The Homebrew cask is untested and stays that way** until someone pushes a
  `v*` tag. That is a release, it is outward-facing, and it is the user's call
  -- do not push one.
- **Plugin discovery** (SPEC005) is withdrawn. **Platform mode** is out of
  scope by design. **windows/amd64** was dropped in SPEC013. None of these is
  pending work; do not "finish" them.

## Traps

- **A guarded find-first step is invisible on a warm graph.** That is the whole
  lesson of "The cold start had never run": five defects hid behind guards that
  returned early because the Python CLI had seeded the graph. Anything you add
  to the seeding path must be tested against an empty graph, which now means
  `down --purge` and a genuine cold start -- not a restart.
- **Do not start a control plane against a throwaway `HMD_HOME` to test
  something.** See item 3: it will recreate the live platform's containers on
  your scratch network. Drive the function under test from a package test with
  a fake Docker seam instead.
- **`make check` and `make test-race` must both stay clean**, and the Robot
  contract suite (`make test-cli`) with them. CI runs all three now.

## Conventions

Conventional commits, one per item, each with the reasoning in the body rather
than the diff. Update CHANGELOG.md (feat/fix/refactor/test only). Update the
NERD as you go: the SPEC's status, its table row, the phase entry, and -- when
you find that the document asserted something untrue -- the "What implementation
changed about the design" list, which is for claims the document made and got
wrong, as distinct from work merely unfinished. Twelve items are in it; the
pattern for each is a bold claim, the SPEC, and the correction.
